How a CUE notification actually travels

Lesson 0001 · the full push flow, end to end

You built this. Now let's understand it. By the end you'll be able to trace exactly what happens between "I created a reminder" and "a notification pops up" — and why it does (or doesn't) appear.

The big idea first

Forget computers for a second. Web Push works exactly like a postal mailbox. Once you've got that picture, every file in your codebase clicks into place.

The mailbox analogy

When you turn on notifications, the browser asks a push provider (Google for Chrome, Mozilla for Firefox) for a mailbox. The provider gives back an address — a long URL. We store that address on our backend.

Later, when a reminder is due, the backend posts a letter to that address. The provider holds the mailbox, so it receives the letter even though our app might be completely closed. It then wakes up the one thing that can read the letter on this device: the service worker. The service worker turns the letter into a system notification.

  • Mailbox address = the subscription's endpoint URL
  • Lock on the mailbox = the p256dh + auth keys (only this device can open it)
  • Postal clerk = the push provider (Google/Mozilla/Apple)
  • Mailbox owner's agent who wakes up = the service worker
  • The letter = the JSON payload: title, body, url

The journey, in 7 hops

  1. User toggles notifications ON
    frontend/nexus-frontend/src/lib/push.js

    subscribeToPush(userId) asks the browser for permission, then calls the push provider and says "I want a mailbox". The provider returns a subscription (the address + the lock).

  2. Frontend stores the mailbox address on the backend
    push.js → fetch POST → PushSubscriptionController → PushSubscriptionService

    The subscription's endpoint, p256dh, and auth get saved to the push_subscriptions table in Postgres. Now the backend knows where to send to this device — and we have the lock key to encrypt to it.

  3. The scheduler ticks (every 60 seconds)
    ReminderScheduler.fireDueReminders() — enabled by @EnableScheduling in NexusBackendApplication

    Like a postman checking his rounds. It asks the database: "which time reminders are past due, and haven't fired yet?" 

    @Scheduled(fixedRate = 60_000)
public void fireDueReminders() {
    List<Reminder> due = reminderRepository.findDueReminders(now);
    ...
}
  4. Scheduler posts the letter
    ReminderScheduler → PushSender (interface) → WebPushSender

    For each due reminder, it calls pushSender.send(...). It does not care how sending works — it just hands over the user, title, body, and a route. That's the PushSender interface: the scheduler only knows what to send, not how.

  5. WebPushSender looks up the device and locks the letter
    WebPushSender.send()

    It finds every mailbox (subscription) this user owns, then encrypts the letter so only that device can open it. The encryption uses the device's p256dh + auth keys — your VAPID private key signs it, proving to the provider that your app (not some random server) is allowed to mail this address.

  6. Provider delivers to the service worker
    the push provider → frontend/nexus-frontend/src/sw.js

    The provider holds the mailbox. It receives the letter and wakes up the service worker — even if the app tab is closed. The service worker's push event fires. 

    self.addEventListener('push', (event) => {
  event.waitUntil((async () => {
    await self.registration.showNotification(title, options)
    ...
  })())
})
  7. The system notification appears
    sw.js → browser notification

    showNotification pops the alert. If an app tab is already open, the service worker also posts a message to it so the in-app banner shows too. When you click the notification, the notificationclick event opens the right page.

Why the scheduler lives on the backend (not the frontend)

This is a great interview answer. Time reminders must fire even when the user has closed their browser. A frontend timer can't do that — it dies with the tab. The backend keeps a single clock, so two tabs never fire the same reminder twice, and it has one source of truth for "has this fired?" (the fired flag).

So… why doesn't it fire on my laptop?

The honest answer

Your code is probably correct. The most likely culprit is that desktop Chrome on localhost is notoriously unreliable for push — it often suppresses or delays push from http://localhost for power and UX reasons. Push is designed for HTTPS + real devices. That's exactly your deploy target (Vercel + mobile). So "nothing on my laptop" does not mean it's broken.

Your task: check each link in the chain

Instead of trusting me, verify it yourself. The chain has ~6 links, and each one can break independently. When a notification doesn't arrive, walk this checklist:

  1. Is the backend even running? If not, no scheduler tick → no letters. (This is the #1 cause.)
  2. Is the service worker registered? DevTools → Application → Service Workers. If no SW, push can't be received.
  3. Is there a subscription in Postgres? If push_subscriptions is empty, the backend has no address to mail to.
  4. Is the reminder due and unfired? Check remindAt <= now and fired = false.
  5. Are the VAPID keys the same on frontend AND backend? A mismatch = provider rejects the letter.
  6. Did the user grant permission? If Notification.permission isn't granted, nothing shows.
Checkpoint — grill yourself

Before moving on, answer these in your head (say them out loud):

  • Where does the "mailbox address" get stored? (Hop 2 — Postgres)
  • What wakes up when a push arrives? (The service worker, even if the tab is closed)
  • Why can't a frontend timer do the scheduler's job? (It dies with the tab)
  • What does the VAPID key prove? (That your app, not any server, may send to this mailbox)
Checkpoint — do it

In your terminal, when the backend is running, check the scheduler log. Create a reminder 2 minutes in the future, then watch the backend log for "Firing N due reminder(s)". If you see it, the backend half of the chain works. If not, the reminder isn't reaching a due state.
